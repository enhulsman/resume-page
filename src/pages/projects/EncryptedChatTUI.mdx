This started as a Computer Security course project, and I kept going with it because building a chat system from scratch in Rust teaches you things you can't learn any other way. Serialization, concurrency, protocol design, all of it hits different when you're wiring real TCP connections to a real database with a real UI on top.

The project is a Cargo workspace with three crates, built with one collaborator who contributed initial project scaffolding.

- **Common protocol library**: Defines all request and response types as tagged enums with structured error codes, shared user types, and a newline-delimited JSON codec. The protocol is the single source of truth. Adding a new message type is one enum variant, and the compiler enforces exhaustive handling on both sides.
- **Async server**: Tokio-based, spawns a task per TCP connection, decodes typed requests from the wire, dispatches them through a central handler, and responds with encoded JSON. PostgreSQL persistence via sqlx with compile-time checked queries that validate against the actual database schema at build time. Migrations run automatically on startup.
- **Terminal client**: Cursive TUI with a persistent connection layer that bridges network I/O to the synchronous UI event loop. Two dedicated threads (one for writing requests, one for reading responses) communicate with the main thread through channels, keeping the interface responsive over a single long-lived TCP connection. The connection sends a clean disconnect on teardown and documents its ordering invariants explicitly.

## The Architecture

**Compile-time checked SQL.** All database queries are validated against the Postgres schema at compile time via sqlx macros. A cached query metadata directory means CI and fresh clones build without a running database, which is honestly one of the nicest things about sqlx.

**Hacker-themed rank system.** Users progress from "Newbie" through "Zero-Day Hunter" to "Root Admin" based on account age. It's pure personality, but it makes the whole thing feel like something you'd actually want to use in a terminal.

## Design Choices

**ndjson over raw text.** The original protocol was just string-matching on plaintext commands with manual slicing, which lasted about a week before I got tired of mysterious parsing bugs. Replacing it with typed newline-delimited JSON and a shared enum gave both sides structured serialization, typed error codes, and a compiler-enforced contract. Adding a new request type won't compile until both server and client handle it.

**Threaded connection bridge.** Cursive runs a blocking event loop, so I couldn't just throw async networking in there. The solution was pretty straightforward: split the socket across two threads and use channels. The UI sends requests synchronously while network reads happen in the background, and the whole thing stays responsive without fighting the framework.

## Where It Is

The server accepts concurrent connections and handles user lookup and listing with PostgreSQL-backed persistence. The registration flow works end-to-end through the UI and protocol, with the database write as the next piece to wire in. The client provides a working TUI with a login flow, user listing, an in-app command terminal, and the rank system. The full request-response lifecycle works over persistent connections.

## What's Next

The protocol already defines message types for authentication, direct messaging, message history, and status updates. The wire format and error codes are in place, so the next phase wires them to real handlers. TLS will encrypt all connections, JWT-based auth will handle sessions, and a server-push channel (sketched into the client's connection architecture) will enable real-time message delivery. The goal is a fully encrypted, self-hostable chat system with a single-command Docker Compose deployment for production.
